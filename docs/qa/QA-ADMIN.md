# QA — админ-панель (`admin/`), два прохода: legacy → attested

> **Область.** Только UI админки и её путь до companion. Находки волны безопасности
> (H1, H2, M1, L1–L3) и приложение — в соседнем `QA-SECURITY-WAVE.md`; здесь они
> не повторяются, только ссылки.
>
> **Почему этот документ вообще есть.** У админки **нет ни одного E2E-теста**. Всё,
> что ниже, сегодня проверено только чтением кода. Любой шаг, который не сойдётся,
> — это первое живое наблюдение, а не подтверждение известного.
>
> **Разделение с `QA-SECURITY-WAVE.md`:**
>
> | Тема | Где |
> |---|---|
> | Пересборка companion, миграция 0010, env, порядок включения attested | там, §0.1–0.4 |
> | M3 через curl (роль подделывается в legacy, не подделывается в attested) | там, §2.4a / §2.4b |
> | Риск «attested при неготовой админке» | там, §4.4 |
> | **Клик-проход по разделам панели, что видит живой оператор** | **здесь** |
> | **Что видит оператор при НЕВЕРНОМ секрете** | **здесь, §2.4** |
> | **Какие разделы вообще не имеют companion-эндпоинта** | **здесь, §3** |

## 0. Предусловия

### 0.1 Сначала — общий блок
Выполнить `QA-SECURITY-WAVE.md` §0.1 (пересборка + миграция 0010) и §0.2 (env).
Без применённой 0010 часть проверок ниже упадёт по причинам, не связанным с админкой.

### 0.2 Режим админки — обязательно этот
```
NEXT_PUBLIC_DATA_MODE=api
ADMIN_BACKEND=companion
```
**Только эта пара что-то доказывает.** В mock-режиме UI работает на
`mockDataProvider` (ноль сетевых запросов) и рисует фикстуры — панель будет
выглядеть рабочей, не коснувшись companion ни разу.

С недавних пор `companionEnabled()` требует обе переменные: при
`ADMIN_BACKEND=companion` без `NEXT_PUBLIC_DATA_MODE=api` запросы молча уйдут
на Supabase-путь, а не в companion. Если разделы показывают пусто/ошибку —
проверить эту пару **первой**, до всякой отладки companion.

Также нужны в `admin/.env`:
```
COMPANION_ADMIN_URL=http://localhost:6062      # или внутренний DNS companion
COMPANION_ADMIN_SECRET=<совпадает с companion COMPANION_ADMIN_SECRET>
ADMIN_SESSION_SECRET=<>=32 символов>
SUPABASE_URL / SUPABASE_SECRET_KEY             # нужны: AdminUser живёт там
```

### 0.3 Нужен настоящий логин оператора
Раньше списки открывались без сессии — это была дыра (#19), теперь `GET
/api/admin/[resource]` и `/[id]` требуют сессию, как и мутации. Поэтому:

1. Открыть `/login`, войти реальным админом.
2. Проверить, что кука `anoon_admin` выставилась (DevTools → Application → Cookies).

**Если панель редиректит на `/login` по кругу** — не спешить винить #19: сначала
проверить `ADMIN_SESSION_SECRET` (при <16 символов `verifySession` всегда
возвращает null, и цикл выглядит одинаково).

### 0.4 Нужен второй аккаунт с ролью `moderator`
Ролевой гейт — единственное место, где роль реально что-то решает, и без
модератора его не проверить.

**Ловушка:** `scripts/create-admin.mjs` хардкодит `role: "super_admin"` (строка 26)
— вторым запуском модератора не создать. Варианты:
- завести админа скриптом и вручную поменять `AdminUser.role` на `moderator` в Supabase;
- либо вставить строку напрямую (пароль — argon2id-хэш, открытый не подойдёт).

Записать оба набора учёток — они нужны в §1.3, §1.4, §1.6 и §2.3.

### 0.5 Порядок двух проходов — не менять местами
Сначала **весь §1 (legacy)**, потом **§2 (attested)**. Legacy — то, что отгружается;
он обязан пройти. Attested — то, что включают позже, и его провал не должен
маскироваться провалом legacy.

## 1. Проход 1 — legacy (дефолт, ОБЯЗАН пройти)

`COMPANION_ADMIN_TOKEN_SECRET` на companion **не задан**. Личность оператора
берётся из заголовков `X-Admin-Id`/`X-Admin-Role`.

**Проверить до начала:** в логе старта companion есть строка вида
`admin operator identity: legacy headers ... asserted, not attested`.
Если там `attested` — секрет где-то задан, и вы делаете §2, а не §1.

### 1.1 Обзор (`/overview`)
- Открыть. **Ожидается:** карточки — всего пользователей, онлайн (ж/м/скрытые),
  открытые жалобы, активные баны; числа не все нули, если в БД есть данные.
- **Если все нули при непустой БД:** запрос ушёл не в companion. Проверить §0.2.
- **Если 502 / «companion недоступен»:** companion не поднят или неверный
  `COMPANION_ADMIN_URL`.
- Сверить руками: `select count(*) from users;` в БД companion ≈ «всего».

### 1.2 Онлайн (`/online`)
- Открыть при живой сессии хотя бы одного пользователя в приложении.
- **Ожидается:** пользователь появляется в списке; фильтр по полу переключает выдачу.
- Окно «онлайн» — 90 секунд (`onlineWindow`, admin.go). Пользователь пропадает
  примерно через полторы минуты после закрытия приложения — **это не баг**.
- **Если пусто при живом пользователе:** presence не пишется — смотреть
  `touchPresence`, не админку.

### 1.3 Жалобы (`/reports`) — список + смена статуса
- **Ожидается:** список жалоб, пагинация, фильтр по статусу.
- Сменить статус жалобы на «в работе» → строка обновилась.
- Сменить на «разобрано с баном» → **пользователь из жалобы забанен**; проверить
  в `/users` и в БД: `select * from bans where user_id=...`.
- **Важно:** бан по жалобе — **перманентный**, значит только super_admin.
  Под модератором это действие обязано отдать 403 (см. 1.6).
- Открыть карточку одной жалобы (`/reports/<id>`) — она идёт через
  `GET /api/admin/[resource]/[id]`, тот самый роут, которому в #19 добавили
  проверку сессии. **Ожидается:** открывается. Если 401 — регрессия #19.

### 1.4 Пользователи (`/users`)
- Список: `#ID`, ник, онлайн-точка, число жалоб, признак бана.
- Открыть карточку пользователя (`/users/<id>`) — снова путь `[id]`.
- **Временный бан** (со сроком) под **модератором** → должен пройти.
- **Мьют / размьют** под модератором → должен пройти.
- **Перманентный бан** (без срока) под модератором → в UI опции не должно быть
  вовсе (`allowPermanent={false}`, ban-dialog.tsx:27).
- Разбан под модератором → кнопки не должно быть (`isSuper`, users/page.tsx:31).
- Всё то же под super_admin → доступно и срабатывает.
- После бана проверить, что в Tinode сессия пользователя реально рвётся
  (пользователь выбрасывается из приложения). Если состояние в БД поменялось,
  а сессия жива — это рассинхрон companion↔Tinode, ищите строку
  `tinode ban ... failed` в логе.

### 1.5 Баны (`/bans`)
- Список активных банов.
- Снять бан под super_admin → состояние `lifted`, пользователь снова входит.
- Под модератором кнопки снятия быть не должно.

### 1.6 Ролевой гейт на сервере — отдельно от UI
UI прячет кнопки, но это **не граница безопасности**. Проверить сервер напрямую:

```bash
# Модератор пытается перманентно забанить (без expiresAt) — мимо UI
curl -s -X PATCH http://localhost:6062/admin/users/1 \
  -H "X-Companion-Admin-Secret: $COMPANION_ADMIN_SECRET" \
  -H "X-Admin-Id: op-mod" -H "X-Admin-Role: moderator" \
  -H 'Content-Type: application/json' -d '{"banned":true}'
# ОЖИДАЕТСЯ: 403 forbidden
```
```bash
# И тут же — почему legacy это лишь ширма: тот же вызов с подделанной ролью
curl -s -X PATCH http://localhost:6062/admin/users/1 \
  -H "X-Companion-Admin-Secret: $COMPANION_ADMIN_SECRET" \
  -H "X-Admin-Id: кто-угодно" -H "X-Admin-Role: super_admin" \
  -H 'Content-Type: application/json' -d '{"banned":true}'
# ОЖИДАЕТСЯ: 200. Это ЗАДОКУМЕНТИРОВАННОЕ поведение legacy, а не находка.
# Ровно это и чинит attested-режим (§2).
```
Подробнее по этой паре — `QA-SECURITY-WAVE.md` §2.4a.

### 1.7 Рассылка (`/broadcast`)
- Под **модератором**: страница показывает «Массовая рассылка доступна только
  super_admin» (broadcast/page.tsx:62), формы нет.
- Под **super_admin**: отправить тестовую рассылку.
  **Ожидается:** ответ `{sent, total}`; на подписанном устройстве приходит пуш.
- **Если `sent: 0` при наличии подписок:** VAPID не настроен — push.Service
  документированно молчит без ключей. Это конфигурация, не баг рассылки.
- Фильтр по полу: «все» / «девушки» / «парни» — companion принимает только
  `male|female`, «все» не шлёт поле вовсе.

### 1.8 Файлы (`/media`) и Галерея (`/gallery`)
- `/media` — папки по владельцам со счётчиками; провалиться в папку.
- `/gallery` — общая лента с `#ID` на тайлах, фильтры по дате и типу.
- **Ожидается:** идут в companion (`GET /admin/media`, `/admin/media/folders`).
- **Известное ограничение, не баг:** companion отдаёт `url` как есть, без
  подписанных ссылок (в отличие от Supabase-пути). Если превью не грузятся —
  смотреть доступность файла в Tinode, а не админку.
- **Модерация медиа из UI в companion не уедет** — см. §3.

### 1.9 Чаты (`/chats`)
- **Ожидается: фикстуры или Supabase, НЕ companion.** Это осознанно, см. §3.
  Пустой или «ненастоящий» раздел здесь — не баг.

## 2. Проход 2 — attested

Смысл прохода: `X-Admin-Role` перестаёт быть словом на веру. Плюс — единственный
режим, где неверная настройка кладёт **всю** панель разом, а не деградирует;
это поведение никто ещё не наблюдал живьём.

### 2.1 Порядок включения — строго такой
Совпадает с `QA-SECURITY-WAVE.md` §0.3; повторяю, потому что перестановка шагов
даёт 401 на всё.

1. **UI уже шлёт токен** — это в коде (`companion-client.ts`, `authHeaders`),
   отдельно включать нечего. Убедиться, что задеплоена свежая админка.
2. На companion выставить `COMPANION_ADMIN_TOKEN_SECRET` = **точно** значение
   `ADMIN_SESSION_SECRET` админки, символ в символ.
3. Перезапустить companion.
4. В логе старта: `admin operator identity: attested`.

**Перелогинивать операторов не нужно** — существующая кука уже подписана этим же
ключом, companion просто начинает её проверять. Живые сессии переживают
переключение. Если оператора всё же выкинуло — кука старше 8 часов (TTL), обычный
релогин.

### 2.2 Панель работает как раньше
Быстро повторить §1.1, §1.3, §1.4, §1.8. **Ожидается:** ничего не изменилось.
Личность теперь берётся из токена, но у легального оператора она та же.

### 2.3 Роль больше не подделывается — главная проверка
```bash
# Тот же вызов, что дал 200 в §1.6: подделанная роль в заголовке.
curl -s -X PATCH http://localhost:6062/admin/users/1 \
  -H "X-Companion-Admin-Secret: $COMPANION_ADMIN_SECRET" \
  -H "X-Admin-Id: кто-угодно" -H "X-Admin-Role: super_admin" \
  -H 'Content-Type: application/json' -d '{"banned":true}'
# ОЖИДАЕТСЯ: 401 invalid_admin_token — токена нет вовсе.
# Было 200 в legacy. ЭТО и есть починка M3.
```
```bash
# С настоящим токеном МОДЕРАТОРА (взять из куки anoon_admin в DevTools):
curl -s -X PATCH http://localhost:6062/admin/users/1 \
  -H "X-Companion-Admin-Secret: $COMPANION_ADMIN_SECRET" \
  -H "X-Admin-Token: <кука модератора>" \
  -H "X-Admin-Role: super_admin" \
  -H 'Content-Type: application/json' -d '{"banned":true}'
# ОЖИДАЕТСЯ: 403. Заголовок роли игнорируется, роль берётся из клейма токена.
```
Второй вызов — суть режима: **оператор не может повысить себе права**, даже имея
общий секрет. Если пришло 200 — attested не включился, проверить §2.1 шаг 4.

Заодно: в `moderator_actions` авторство теперь равно `sub` токена, а не тому, что
прислали. Посмотреть строку последнего действия — там должен быть реальный
`AdminUser.id`.

### 2.4 Намеренная поломка — что видит оператор в 2 часа ночи
Ради этого шага проход и затевался.

**Сначала — ловушка, из-за которой шаг легко провести неправильно.** Неверный
секрет должен быть **не короче 16 символов**. Иначе companion **не стартует
вовсе** (`config.Load` отказывается), и вы будете диагностировать упавший
контейнер вместо 401. Брать заведомо длинную неверную строку:

```
COMPANION_ADMIN_TOKEN_SECRET=этот-ключ-заведомо-не-тот-и-он-длинный
```

1. Выставить неверный (длинный) секрет, перезапустить companion.
2. Открыть панель, зайти в «Жалобы».

**Ожидается:** раздел не грузится, показывает ошибку. Панель **не** должна
отрисоваться наполовину и не должна показать пустой список так, будто данных нет
— пустой список выглядел бы как «жалоб нет», и это худший исход.

**Что именно увидит оператор — записать фактически.** Ниже ожидание из чтения кода
(не наблюдение — ради его проверки шаг и делается). Трассировка сверена с
agent-scaling.

`companionFetch` (`companion-client.ts:99`) бросает `Error` с сообщением из поля
`error` ответа companion, то есть **`invalid_admin_token`**. Дальше каждый роут
переоборачивает исключение по-своему, и статусы получаются РАЗНЫЕ:

| Раздел | Статус в браузере | Где |
|---|---|---|
| Списки (жалобы, пользователи, баны) | **400** | `[resource]/route.ts:39` |
| Обзор / Онлайн | **400** | `overview/route.ts:63,106` |
| Чаты | **400** | `chats/route.ts:140` |
| Файлы — карточка | **400** | `media/route.ts:217` |
| **Файлы — список, и Рассылка** | **502** | `media/route.ts:100`, `broadcast/route.ts:48` |

**Тело во всех случаях одно: `{"error":"invalid_admin_token"}`.** Строка
«companion недоступен» в 502-ветках — это фолбэк только для не-`Error` исключений,
и при рассинхроне ключа она НЕ появится. То есть:

- **статус врёт** — 502 читается как «companion лежит», хотя companion жив и
  отказал в авторизации. Это худший ложный сигнал из всех, и он приходится ровно
  на два раздела, которые проходятся кликами: **Рассылка** и **Файлы (список)**;
- **тело говорит правду** — смотреть надо на него, а не на код статуса.

Тестировщику: при подозрении на рассинхрон ключа открыть DevTools → Network и
читать **тело** ответа, а не полагаться на статус.

**Различать два разных отказа** (легко перепутать, лечится по-разному):

| Что видно | Что это | Что делать |
|---|---|---|
| `401`, тело `{"error":"unauthorized"}` | Нет куки оператора. Проблема в панели, не в companion (`[resource]/route.ts:21`) | Залогиниться заново |
| `400` или `502`, тело `{"error":"invalid_admin_token"}` | Ключи не совпали. Проблема в companion | Сверить `COMPANION_ADMIN_TOKEN_SECRET` = `ADMIN_SESSION_SECRET` |

Если разнобой статусов подтвердится живьём — завести мелкой задачей: пробрасывать
401 companion наружу как 401, и уж точно не как 502.

3. В логе companion на каждый запрос: `admin: rejected PATCH /admin/... : ...`.
   **Если строк нет** — запрос не дошёл до companion, проблема в другом месте.
4. Вернуть верный секрет, перезапустить, убедиться что панель ожила.

### 2.5 Откат
Убрать `COMPANION_ADMIN_TOKEN_SECRET`, перезапустить. В логе снова `legacy headers`,
панель работает. Откат мгновенный и **без передеплоя UI** — админка продолжает
слать токен, companion просто перестаёт его читать.

## 3. Разделы без companion-эндпоинта — баг или недоделка?

Чтобы тестировщик не заводил баги на нереализованное.

| Раздел | companion-эндпоинт | Что ожидать при `ADMIN_BACKEND=companion` |
|---|---|---|
| Жалобы | `GET/PATCH /admin/reports` | Полностью живой |
| Пользователи | `GET/PATCH /admin/users` | Полностью живой |
| Баны | `GET/PATCH /admin/bans` | Полностью живой |
| Обзор / Онлайн | `GET /admin/overview`, `/admin/online` | Полностью живой |
| Файлы / Галерея | `GET /admin/media`, `/admin/media/folders` | **Чтение живое**, см. ниже |
| Рассылка | `POST /admin/broadcast` | Живая |
| **Чаты** | **нет** | **Фикстуры / Supabase — так и задумано** |

**Чаты** заблокированы юридическим вопросом Q7a (`COMPANION-PLAN.md` §7, USER-1
#67): доступ модератора к переписке не разрешён, поэтому companion-путь намеренно
не сделан. Раздел остаётся на Supabase даже при `ADMIN_BACKEND=companion`.
**Не баг. Не заводить.**

**Файлы/Галерея — чтение живое, модерация нет.** На companion есть
`PATCH /admin/media/{id}`, но в `companion-client.ts` для него **нет функции**, а
`resourcePath()` не знает ресурса `media`. Значит любое действие модерации над
медиа из UI **уйдёт на Supabase, а не в companion**. Читается из companion,
модерируется мимо него. Это расхождение, а не отсутствие фичи — стоит завести
задачей, если подтвердится на живом стенде.

**Внимание на устаревшую строку в документации:** `PROJECT-STATUS.md` (таблица,
строка про админку) говорит «chats/media/broadcast — нет endpoint». Для media и
broadcast это **уже неверно** — эндпоинты есть. Актуально только про chats. Не
ориентироваться на эту строку при триаже; её стоит поправить отдельно.

## 4. Чек-лист «прошло / не прошло»

**Проход 1 — legacy (блокирующий):**
- [ ] В логе старта companion — `legacy headers`
- [ ] Логин оператора, кука `anoon_admin` выставлена
- [ ] Обзор: ненулевые счётчики, сходятся с БД
- [ ] Онлайн: живой пользователь виден
- [ ] Жалобы: список, смена статуса, карточка `/reports/<id>` открывается
- [ ] Жалоба → бан: пользователь реально забанен, сессия в Tinode разорвана
