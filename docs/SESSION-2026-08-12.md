## 1. Что лежало в рабочем дереве и уехало в прод

Четыре коммита, `50253e9..b1a28f1`, запушены и выкачены.

### `e4f59d4` — `peerOnline` с грейсом

`GET /roulette/status` отдавал `peerOnline` из `Hub.Online()` — «есть ли сокет
прямо сейчас». Клиент (`restoreActiveMatch`) при `peerOnline=false` не просто
отказывается восстанавливать анонимный чат, а **завершает матч**. Итог: оба
перезагрузились одновременно — каждый прочитал другого как ушедшего и каждый
разорвал чат, из которого никто не уходил.

`Hub.RecentlyOnline()` — сокет есть ИЛИ последний отвалился меньше
`wsDisconnectGrace` (20 с) назад, то же окно, что сервер выжидает в
`endMatchOnDisconnect`. Использует **только** `peerOnline`; звонки, подавление
пушей и админский список онлайна оставлены на мгновенном `Online()` — там грейс
дал бы неверный ответ.

Комментарий в `roulette.go` уже год утверждал, что перезагружающийся пир
считается онлайн. Это было неправдой: грейс жил только на стороне закрытия
матча.

### `f03cabb` — отправитель видит свою загрузку

Жалоба «видео не отправляется» = два дефекта, оба на стороне отправителя:

1. оптимистичный пузырь создавался **после** `await uploadFile`. Пир сразу
   видел «отправляет медиа…», отправитель — пустой экран. На телефонном видео
   это минута тишины после нажатия, неотличимая от мёртвой кнопки;
2. файл больше `media.max_size` (32 МБ) грузился целиком, получал голый 413 и
   показывался тем же «Не удалось отправить», что и любой другой отказ.

Оба закрыты одним действием `uploadAndSendMedia(scope, file, kind, opts)` в
`frontend/src/store/slices.ts`: свой прогресс-пузырь, проверка размера до
загрузки, отдельная формулировка про лимит, `isTooLargeError` для серверного
413. На него переведены оба чата и оба пути голосовых — раньше это были четыре
копии одного кода с одними дефектами. Мобильный composer теперь только читает
байты (`pickMedia`, `voiceBlob`), загрузку ведёт стор.

### `a9e039c` — три тап-таргета меньше 24 px

**`next build` дописывает свой dist-каталог в `tsconfig.json`.** Сборка в новый

status`.**

Плюс: `npx expo lint` тянет CLI из npx-кеша, тот не видит `eslint` из проекта и
падает с `Cannot find module 'eslint'`. Работает только `npm run lint` из

## 3. Телефон вместо железа — задача о запуске на устройстве сдвинулась

Запуск мобильного приложения упирался в отсутствие `adb`, `ANDROID_HOME` и
входа в Expo. Выяснилось, что железо не нужно: хватает телефона владельца и
облачной сборки EAS.

**`eas init` сделан.** Проект привязан к аккаунту `hke700`,
`projectId 815b9644-e707-43bc-accd-4cf6652bbaa5` записан в `mobile/app.json`.
Пуш-токены Expo выдаются на проект, так что до этого пуши на телефоне не могли
работать в принципе.

**Expo Go не подходит — и это не чинится.** Три независимых стопора:

1. Expo Go из Play Market собран под последний **выпущенный** SDK, проект — на
   57. Приложение честно отвечает `Project is incompatible with this version of
   Expo Go`, а «более новой версии» не существует;
2. `react-native-webrtc` (звонки) — нативный модуль, которого в Expo Go нет;
3. Google-вход в Expo Go отключён в коде: клиент живёт на `exp://`, который
   Google для нативных client id не примет.

**Работаем через development build.** Поставлен `expo-dev-client` (без него EAS
отказывается собирать профиль `development`), собран APK:
`expo.dev/accounts/hke700/projects/anoon/builds/02e998ed-f8e3-492b-9b3c-93c57f9a76b1`.
APK ставится **один раз**; дальше код берётся с компьютера
(`npx expo start --dev-client`, телефон подключается на
`http://<LAN-IP>:8081`), правки прилетают без пересборки. Пересборка нужна
только при добавлении нативного модуля.

Сборка ходит в прод (`EXPO_PUBLIC_BACKEND_URL` в `eas.json`), то есть данные
настоящие.

## 4. Что осталось за владельцем

**Google-вход на телефоне** — нужен отдельный OAuth client id типа **Android**
(веб-клиент не годится: Google не пускает custom-scheme redirect для клиентов
типа Web). Package `com.anoon.app`, SHA-1 берётся из уже созданного keystore
(`eas credentials -p android` либо expo.dev → Credentials). После этого:
`EXPO_PUBLIC_GOOGLE_CLIENT_ID_ANDROID` в `eas.json` + оба id в
`COMPANION_GOOGLE_CLIENT_IDS` на проде, иначе companion отвергнет токен с
телефона как `invalid_token` (сверяется `aud`).

Полезное следствие development-сборки: client id попадает в бандл, который
собирает **компьютер**, а схема возврата `com.anoon.app://` вшита в любую
сборку (она равна имени пакета). Значит Google-вход можно будет включить и
проверить **без новой облачной сборки**.

**SMTP** — по-прежнему отложен, письма пишутся в лог.
