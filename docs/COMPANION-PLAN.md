## 0. Что проверено в исходнике Tinode (факты, не догадки)

Две gRPC-механики:
- **`Node`** (Tinode = сервер, мы = клиент, поток `MessageLoop`). ROOT-клиент через `on_behalf_of`
  может действовать от имени любого юзера, в одном потоке — за многих сразу
  (`session.go:480-505`). ROOT даётся только аккаунту, помеченному через `tinode-db --make_root`.
- **`Plugin`** (мы = gRPC-сервер, Tinode звонит нам). `FireHose` — синхронный перехват КАЖДОГО
  входящего пакета на горячем пути (`session.go:471`), может DROP/RESPOND/REPLACE. По умолчанию
  **fail-open** (`failure_code:0` → если плагин лёг, запросы проходят). `Find` — может полностью
  подменить результаты поиска на топике `fnd` (`plugins.go:462-470`) → годится под #ID и рулетку.
  События Account/Topic/Sub/Message — post-commit уведомления, поведение менять НЕ могут.

Ключевые ограничения:
- **АНОНИМНОСТЬ нативно невозможна.** P2P-топик: имя топика = `usrXXX` пира, его Public отдаётся
  всегда (`init_topic.go:289`, `topic.go:2118`). Group-топик: участники всегда видят UID + Public
  друг друга (`topic.go:2633,2693`), флага «скрытый участник» нет. `read/recv/печатает` несут
  реальный UID в `From` (`topic.go:1255-1267`). Единственное обезличивание — **channel** (`From=""`,
  `topic.go:279-280`), но односторонний (только читатели).
- **Бан** = ROOT шлёт `{acc state:"susp"}` на UID → `changeUserState` (`user.go:556`) вышибает все
  сессии + блокирует вход. Разбан — `state:"ok"`.
- **OAuth** нативно нет. Есть схема **`rest`** (`auth/rest/`): Tinode POST-ит на внешний HTTP-сервис,
  тот валидирует и возвращает UID (или создаёт аккаунт авто). Это наш хук под Google/FB/Apple.
- **Email-подтверждение и сброс пароля** встроены, но нужен рабочий **SMTP** в конфиге.
- **«Системное» сообщение** в топик: либо имперсонация выделенного system-аккаунта (ROOT
  `on_behalf_of`), либо запись в root-only топик `sys`.

## 1. ГЛАВНАЯ РАЗВИЛКА — как реализовать анонимный чат-рулетку

Всё остальное зависит от этого. Личность нельзя светить до «Раскрыть профиль». Варианты:

- [ ] **A. Companion сам транспорт для анонимной фазы (НЕ Tinode).**
  Анонимный чат идёт целиком через companion (свой WS): companion релеит сообщения, хранит их,
  личность не выдаёт вообще. На «раскрытие» → создаём реальную p2p-дружбу в Tinode и мигрируем.
  - `+` полная гарантия анонимности; полный контроль над рулеткой/оценкой/view-once.
  - `−` для анон-фазы сами реализуем «печатает», статусы, медиа, пуши (Tinode не участвует).
- [ ] **B. Маск-аккаунты (прокси-личности) в Tinode.**
  На каждого юзера (или на матч) companion держит «маску»: аккаунт с Public = {«Собеседник», #ID}.
  Анон-чат = group-топик, обе стороны заведены масками; сообщения ретранслирует companion (ROOT
  `on_behalf_of` маски). Реальный UID не появляется.
  - `+` переиспользуем движок Tinode (статусы/медиа/печатает) в анон-фазе.
  - `−` двойная личность (реальный клиент ↔ маска) → сложный мост, риск утечки при ошибке.
- [ ] **C. Гибрид: Tinode только для друзей, рулетка — на companion.**
  Как A, но честно принимаем: анонимная фаза беднее по фичам, зато безопасна и проста; вся
  «богатая» переписка (медиа, реакции, звонки) живёт у друзей на Tinode.
  - `+` самый простой и безопасный старт; чёткая граница ответственности.
  - `−` часть UI анон-чата (медиа/голос) надо гонять через companion.

- [ ] **D. Channel-режим two-way (родной Tinode, без масок).**
  Анон-чат = один топик, обе стороны подписаны через channel-алиас. Tinode сам обнуляет `From=""`
  и не отдаёт channel-читателю список других подписчиков. Если two-way работает — жёсткая
  анонимность даром, ноль лишних аккаунтов, полный движок. `?` требует проверки исходника
  (может ли channel-читатель публиковать и получать сообщения друг друга).
- [ ] **E. Мини-патч сервера (родной Tinode + микро-форк).**
  Собираем Tinode из исходника → добавляем спец-тип топика, который на рассылке обнуляет `From`,
  прячет UID/Public участников в `{meta sub}` и `From` в `{info}/{pres}`. Родной движок, ноль
  масок. Цена — маленький локальный патч (расхождение с upstream, чуть сложнее апгрейды).

**Итог разведки исходника (2026-07-03):**
- **D — ❌ НЕ РАБОТАЕТ.** Channel-подписчик не может писать (`ModeCChnReader` без `W`,
  `types.go:571`; `{pub}` reject `topic.go:1004`). Каналы односторонние. Отпадает.
- **E — ✅ МАЛЕНЬКИЙ ПАТЧ.** Анон-чат = обычный group-топик между двумя реальными аккаунтами +
  флаг «анонимный». Точки: `prepareBroadcastableMessage` `topic.go:279` (глушим `Data.From` +
  `Info.From` — закрывает live-сообщения и «печатает»/статусы), `replyGetData` `topic.go:2794`
  (история), `replyGetSub` `topic.go:2633/2693` (UID/Public/Trusted пира в meta sub). Presence
  выключаем через отсутствие бита `P` (`topic.go:241`). ~3 точки + 1 флаг. Родной движок,
  ноль масок, ноль churn, жёсткая анонимность. Цена — микро-патч переналагать при апгрейде.

❓ **Q1 — РЕШЕНИЕ.** Рекомендация — **E (маленький патч)**: единственный вариант, что даёт
одновременно жёстко + медиа/голос + родной Tinode + без минусов масок. B (маски) остаётся
запасным, если патчить ядро принципиально не хотим.
❓ **Q1a.** Насколько «анонимность» юридически критична (18+, риск)? Мягкая (клиент не показывает) или
жёсткая (сервер физически не отдаёт)? От этого зависит, допустим ли вообще вариант B.
❓ **Q1b.** В анон-фазе нужны медиа/голосовые сразу, или на старте только текст + «печатает»?
